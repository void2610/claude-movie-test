# motion エンジンの設計判断 (2026-10-04)

## 方針

- @shneural のエンジン (`shneural-engine-anatomy.md`) を下敷きにしつつ、作品ごとの定数をハードコードせず、`Composition` に寄せて使い回せるようにした
- 作品は `projects/<名前>/project.py` の `build()` で組み立てる。エンジンと作品を分け、作品は短いコードで書けるようにする

## 判断と理由

- **`f(t)` で決定的に描く**: フレームを並列にばらばらの順で描くため。モーションブラーのサブフレームも同じ関数を `t ± dt` で呼ぶだけで済む
- **ワーカーごとにプロジェクトを読み直す (spawn)**: skia のオブジェクトは pickle できない。親プロセスは RGB のバイト列を受け取り、順番どおり ffmpeg に rawvideo でパイプする (PNG を経由しないので速い)
- **`Scene.setup` で前計算**: 粒子などのシミュレーションは時間方向に依存するため、ワーカーごとに一度だけ全区間を計算してキャッシュし、描画は補間で引く
- **`Composition.prepare` はメインプロセスで実行**: Blender のプレート生成は重く、並列ワーカーが同時に走らせると競合するため
- **`comp.cues` を映像と音で共有**: カメラシェイク・フラッシュ・色収差・効果音のタイミングを 1 か所で定義すると、ずれない
- **ポスト処理の量は 1080p 基準**: `--draft` やコンタクトシートで解像度を落としても、見た目の比率が変わらない
- **文字組みは harfbuzz → skia の TextBlob**: skia 単体の drawString はカーニングもリガチャも効かないため
- **合成はリニア空間、演出は表示空間**: モーションブラーの平均や bloom・色収差を sRGB のまま計算すると、明るい物の縁が濁る。一方、フラッシュやグレインをリニア空間でかけると暗部が大きく持ち上がって灰色になる (フラッシュ 12% が sRGB で約 38%)。そこでポスト処理に `space` 属性を持たせ、リニア → sRGB 変換の前後で分けて処理する
- **トランジションは元の 2 シーンを隠して自分で描く**: シーンに `hidden` 区間を持たせ、`Transition` が `paint_scene` で両方を描く。シーン側のコードはトランジションを意識しなくてよい
- **トランジションは「a の上に b を重ねる」では足りない**: 背景を別シーンに分けると各シーンは透明になり、b の空白から a が透ける。wipe / iris / slices は a を b の領域の外側だけに描き、crossfade は a もフェードアウトさせる (LiminalPalette の動画で発覚)
- **フォールバックは文字単位で書体を切り替える**: Mona Sans に和文が無いため、文字ごとに字形を持つ最初の書体を選び、同じ書体の連続区間ごとに harfbuzz で組む。可変軸はその書体が持つものだけ渡す
- **曲の BPM は拍の回帰直線の傾きから**: librosa の拍位置はフレーム単位 (約 11.6ms) に量子化されており、間隔の中央値だと 128 BPM が 129.2 になる
- **小節頭の推定は低音のアタック + 和音の変わり目**: キックが毎拍ある曲では原理的に曖昧なので、`shift_downbeats(n)` で手動補正できるようにした
- **自作の先読み型ピークリミッター**: pedalboard の `Limiter` (JUCE) は閾値の値に応じて出力レベルが予測しにくく変わり、ラウドネスを目標値に揃えられなかった。リミット → 計測 → ゲイン調整を繰り返して目標の LUFS に収束させる

- **キャプチャは使う区間だけを素材の fps で書き出す**: 長い録画を丸ごと書き出すとディスクを食うので、Clip が使う区間 (TimeMap の各区間 + 0.2 秒の余白) だけを JPEG にする。作品の fps ではなく素材の fps で持ち、間の時刻はブレンドかオプティカルフロー (DIS) で補う。フローはブレンドに比べて二重像が 12px → 2px に減った
- **速度変化は TimeMap で表し、映像と音の両方がそれを引く**: 音は「出力の各サンプル時刻 → 素材の時刻」を写像して補間するので、スローでは自然に音程が下がる。フリーズ中は速度 0 を検出して無音にする
- **書き出しには上限ビットレートを付ける**: グレインは毎フレーム違うノイズなので、CRF だけだと 1080p60 で 75〜123Mbps (24 秒で 230〜370MB) になっていた。上限 24Mbps・12Mbps と見比べても差はほぼ無く、既定を 16Mbps (1080p60 基準で解像度・fps に比例) にした
- **GIF の容量は幅と fps で決まる**: ディザの方式 (sierra / bayer / なし) を変えても 5 秒で 15MB 前後のまま。幅 720・20fps・128 色にして約 7MB。グレインが圧縮を壊すので変換前に hqdn3d でノイズを取る
- **文字の重なりは全コマで、文字の見えている範囲で測る** (liminal_poster で発覚): スタジオで見出しの入りを 0.25 秒遅らせた (`dt`) のを、抜けごと遅らせてコードに取り込み、次の見出しと 0.3 秒重なった。`review` は見切れ・閃き・ループしか見ておらず、エラー 0 件で通っていた。そこで文字を描く関数 (`text.text` / `paragraph` / `Captions`) が、描いている要素に「文字の範囲 (幅 × 大文字の高さ) と不透明度」を残し、`review` が全コマを 1/4 の大きさで描いて別々の要素の文字の範囲を比べる。スタジオも今のコマの重なりを赤枠で示す
  - 要素の範囲 (`Seen.bounds` = 記録の `cullRect`) はクリップを無視し、文字はフォント全体の高さで大きめに取られる。押し上げて切った見出しが自分の小見出しと「重なる」誤検出が出たので、文字の範囲は描いた時点の変換とクリップを当てて別に持つ
  - 入れ替えのクロスフェードでは両方が半分の濃さになるので、両方が不透明度 0.6 以上のときだけ数える。2.5D のカードの中の文字は手前のカードに隠れるので比べない
  - 取り込み直後の liminal_poster では見出しの本文 5.15〜5.40s・小見出し 5.33〜5.40s を検出。最初は `node()` の中の文字しか記録しておらず、demo・devlog・liminal (`node()` を使っていない) は何も調べていなかった。要素で囲まずに描いた文字も、描いたコードの場所 (同じ行から別の場所に描いたものは #2 から) を名前にして記録する。文字列を名前にすると、時刻表示やタイプライターがコマごとに別の要素になった。同じ場所に重ねて描いたもの (影・光彩) は 1 つにまとめる
- **文字の大きさと縁での見切れも全コマで見る** (ManimGX の `inspect` を参考に): 小さすぎる文字は、縦に持ったスマホの画面 (360×780) に収めたときに大文字の高さ 6px (文字の大きさ約 8.5px) 未満。長辺 360px で換算すると、縦長の動画が幅 202px になって厳しすぎた。要素ごとに一番大きく見えるコマで測り (拡大しながら入る途中は数えない)、同じコードの行から描いた要素は 1 件にまとめる。縁での見切れは、画面の外まで続く文字のうち、1 コマで 0.5px 未満しか動かない状態が 0.3 秒続いたものだけ (滑り込む途中は数えない)
  - 指摘には要素を描いたコードの場所を付ける (`project.py:331 › 280` は 331 行から呼んだ関数の 280 行)。node を呼んだときにスタックを遡り、エンジンの外の行を外側から並べる
  - 2026-10-12 時点の 4 作品: 重なり・見切れは 0 件、小さすぎる文字は demo 6・devlog 5・liminal 41・liminal_poster 7 件 (16:9 の作品は 1080p で大文字の高さ 32px 未満が該当)
  - 小さすぎる文字は「注意」に留め、レビューの合否に数えない (2026-10-12)。最初はエラーにして、合意済みの 4 作品で 59 件出た。飾りの文字を例外にしても 33 件が残り、ユーザーから「今の動画が合意した内容だろ？それでエラーが出てるんだったらレビューが違う」と指摘された。合意済みの作品には等倍で大文字の高さ 11〜18px の文字が普通にあり、それを全部通す基準ではほとんど何も拾えない。文字の大きさはデザインの判断なので、合否ではなく気づくきっかけにする。重なりと縁での見切れ (合意済みの作品で 0 件) はエラーのまま
  - 教訓: 新しい検査をエラーにする前に、合意済みの全作品が通ることを確かめる。合意済みの作品で失敗するなら検査の方が間違っている。例外で黙らせると、合意済みの内容を私の判断で覆すことになる
  - 例外は時刻の範囲だけでは同じ時刻の別の文字まで外れるので、`Waiver.elements` で要素を指す
  - 要素で囲まない文字を行番号で指すと、作品の先頭に import を 1 行足しただけで全部外れた。行がずれても変わらない関数名の並びで指し、同じ関数に読ませたい文字が混ざるときは文字列で指すか、`node()` で囲んで名前を付ける

## ハマりどころ

- Surge XT のパッチ (.fxp) は pedalboard の `load_preset` (.vstpreset 専用) では読めない。`raw_state` は `VC2!` + XML 長 (LE) + XML + NUL で、XML の `<IComponent>` が JUCE 独自の Base64 (`<バイト数>.<6bit を LSB から詰めた文字列>`)。中身は Surge の `sub3` チャンク + JUCE の付加データ (`JUCEPrivateData`) なので、.fxp の offset 60 以降のチャンクと差し替えて書き戻す (`audio.surge_load`)
- Surge は状態を書き込んだ直後の処理ブロックでパッチを反映し、その 1 回は無音になる。読み込み後に空の処理を 1 回挟む
- skia-python の可変フォント: `FontArguments().setVariationDesignPosition(pos)` の戻り値を `makeClone` に渡すと指定が失われる。`FontArguments` を変数に保持してから渡す
- skia-python に `SetFourByteTag` は無い。タグは `int.from_bytes(b"wght", "big")` で作る
- 可変フォントでない書体に `getVariationDesignParameters()` を呼ぶと RuntimeError になる
- 可変軸の値は 0.5 単位に丸めてキャッシュする。アニメーションで毎フレーム値が変わると、書体のクローンが際限なく増える

## 性能の目安 (M 系 Mac, 10 コア)

- デモ (1080p60・9 秒・モーションブラー 4 倍・ポスト 5 段・トランジション 3 つ): 540 フレームを約 40 秒 (x264)。`--draft` は 8 秒前後
- 高速化前は 8 秒の版で約 106 秒だった。主因はポスト処理 (bloom・グレインで最大 250ms/フレーム)、各ワーカーでの重複した粒子シミュレーション、x264 と CPU の取り合い
- Blender Cycles (Metal): 初回だけカーネルのコンパイルに約 3 分。以降は 320x180・3 フレームで約 3 秒
